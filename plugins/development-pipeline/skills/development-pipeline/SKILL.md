# Delivery pipeline

You own *delivery*: turning a requirement into shipped, verified work by deciding the process, dispatching the right sub-agent for each stage, making the calls that cross their boundaries, and checking every result against what was actually asked.

**Portability.** The table below names Claude Code's nine sub-agents, one per stage — dispatch them where your runtime supports isolated sub-agent dispatch. Elsewhere (Codex CLI, Cursor, Gemini CLI, Antigravity, or Claude Code without this marketplace), read the *Agent* column as the stage's name and perform every stage yourself in the same session, one at a time, labeling which stage you're in and never blending stages. `.claude/` is Claude Code's convention directory; substitute your harness's own state directory (`.codex/`, `.cursor/`, `.agents/`, or equivalent) and keep the same layout (`design-plan.md`, `testing-plan.md`, `temp/`, `docs/`, `api/`) underneath it.

## The team

| Agent | Owns | Deliverable |
|---|---|---|
| solution-architect | Requirements elicitation + functional spec (*what*) and technical design (*how*): architecture, schema, contracts, migration | `.claude/design-plan.md` Parts 1 & 2, with the index and shared invariants at the top |
| implementation-planner | Execution plan: files, phases, edge cases | `.claude/temp/plan.md` |
| plan-driven-implementer | Faithful execution of `plan.md` (or, in a gated direct fix round, of the selected review findings) — product/application code only, never unit test functions. One dispatch for the whole plan, or fanned out per work package plus one consolidation pass on Sonnet (Workflow 3a/3b) | code changes |
| unit-test-implementer | Sole owner of unit test functions, following the actual implementation (opt-in) | test code changes |
| technical-tester | Test plan + execution with evidence (opt-in) | `.claude/testing-plan.md`, results |
| code-reviewer | Correctness/security/edge-case review (opt-in) | `.claude/temp/code-review.md` |
| document-reader | Distills a source document (API/integration spec, PDF, Word doc, Postman collection) into a reference summary; for a prose-only upstream API contract, also writes the house api-specs shape in the same pass (opt-in) | one markdown file per document in `.claude/docs/`, plus `.claude/api/<service>/api-specs.md` when applicable |
| api-specs-writer | API documentation of this project's own implemented endpoints, written from the code only (opt-in) | `.claude/api/api-specs.md` |
| api-bruno-writer | Bruno collection (OpenCollection YAML) generated from the API doc (opt-in) | `.claude/api/bruno/` |

## Sizing the work

Not every task needs the full pipeline. Pick the route and state it with one line of rationale:
- **Trivial fix or a direct question:** handle it yourself; direct edits only for genuinely trivial, well-understood changes — a typo, a one-line fix, a rename. Anything more goes through the pipeline; do not let "trivial" stretch to cover real work.
- **Small change, clear requirements:** implementation-planner → plan-driven-implementer (one dispatch per work package — see Workflow 3a).
- **Feature with open questions, or any design-heavy change:** solution-architect (functional elicitation *and* technical design in one stage) → implementation-planner → plan-driven-implementer. If requirements are already fully clear, tell solution-architect to skip to the technical design (Part 2) and note that Part 1 is a given.
- **Grill the user yourself before dispatching solution-architect.** Interview the user in this conversation, one question at a time (`grill-me`-style, client mode) — pressure-test the request, surface unstated edge cases and flaws — until you have a solid brief; only then write it and dispatch. This is yours to run, not delegated: solution-architect still elicits and documents its own open questions, but starts from an already-pressure-tested brief, not a raw one-liner.
- **unit-test-implementer, technical-tester, code-reviewer, api-specs-writer, and api-bruno-writer are opt-in, never default.** Ask about them in **one** multi-select question at sizing time — not one per stage, not again later — regardless of change size, plan content, or whether you are running autonomously. A `plan.md` marking a target "unit" names it as in scope for the requirement, not as authorization to dispatch the stage unasked. By default plan-driven-implementer still runs build/lint/tests and reports results and manual steps; you review those and decide whether they satisfy the requirement — that is not a technical-tester or code-reviewer dispatch.
- **Size the code-review stage once it is opted in.** **Review inline yourself** when the change touches at most 2 files, adds no new package, and touches no auth, money/balance, persistence-schema, or concurrency code: read the diff, apply the code-reviewer methodology and severity scale, and write the same `.claude/temp/code-review.md`. Otherwise **dispatch code-reviewer** with `model: sonnet` — model omitted (inherits yours) only when the plan tiers any changed package `complex` or the change hits a sensitive area above. Its brief carries only the changed-file list, the `plan.md` Context Pack path, and the conventions file(s); it reads the changed files and their direct callees/callers, never the wider repo. A re-review follows the tier of the review it re-checks.
- **API contracts are a required input for integration work.** When a workstream calls or implements an HTTP API, point every design, implementation, test, and review brief at the contract: `.claude/api/api-specs.md` for this project's own API, `.claude/api/<service>/api-specs.md` for one it consumes from another service. Vendor a missing upstream spec first (rule below) — never let an agent infer a third party's contract from the calling code.
- **Frontend-consumes-backend is the common case of that rule — no separate agent.** A plan or implementer brief with the frontend calling this project's own backend points at `.claude/api/api-specs.md`, never at the backend source. If that file is missing or stale for the endpoints in scope, dispatch api-specs-writer first.
- **Vendoring an upstream spec is never api-specs-writer's job — it documents this project's own code only.** Every upstream service gets its own subdirectory directly under `.claude/api/`, whatever the source type — never a flat `<service>-api-specs.md` file. Route by source:
  - **Machine-readable spec exists** (OpenAPI/Swagger YAML or JSON, a Postman collection export, another repo's own `api-specs.md`): copy it yourself, verbatim, into `.claude/api/<service>/` — as `api-specs.md` when the source is already in that shape, otherwise under its original filename (`openapi.yaml`, `collection.json`) — with a provenance header (source path/URL, date copied). No agent, no rewriting.
  - **Prose-only source** (PDF, Word doc, wiki/integration guide): dispatch document-reader once, telling it the document is an upstream API contract and giving it the `<service>` slug; it writes `.claude/docs/<vendor>/...md` and, in the same pass, `.claude/api/<service>/api-specs.md` in the house shape. No second stage.
  - Point every consuming brief at whichever of `.claude/api/<service>/api-specs.md` or `.claude/docs/<vendor>/...md` actually holds the contract — don't leave it to be found.
- **This whole pipeline (api-specs-writer, api-bruno-writer, upstream vendoring) is HTTP-only.** gRPC (or any other IDL-defined protocol) is out of scope by design: the checked-in `.proto` already *is* the canonical, machine-readable contract. Point every brief touching a gRPC service — this project's or an upstream's — straight at its `.proto` file(s): no api-specs-writer pass, no document-reader summary, no house `-specs.md` file. Fall back to document-reader only if the `.proto` is genuinely unavailable and the only description is prose.
- **Source documents go through a summary check first.** Before any stage reads an API spec, PDF, Word doc, or Postman collection, check `.claude/docs/` for a summary; if one exists, point the consuming agent at it — never re-read or re-summarize a distilled document. If none exists, fold the choice — dispatch document-reader, or read the original this once — into the same sizing question rather than asking separately.

## Workflow

1. Read the project's `CLAUDE.md`. Triage the rest before reading it — the tracked `.claude/design-plan.md` and `.claude/testing-plan.md`, the working documents in `.claude/temp/` (plan, code-review), the `.claude/docs/` summaries: look at headings and dates first (the design-plan index, a heading grep, file modification times) and read in full only what the chosen route needs. Never re-run a stage whose deliverable is current.
2. Size the work, confirm the route with the user if it deviates from what they asked, and ask about the opt-in stages.
3. Drive the stages in order. After plan-driven-implementer, unit-test-implementer, technical-tester, code-reviewer, and api-specs-writer depend only on its output, not on each other. **Without code review in scope**, dispatch whichever are in scope together in one batch, one dispatch each, rather than in waves. **With code review in scope alongside other post-implementation stages**, code review (dispatched or inline) and its fix/re-review loop (step 6) run first, to completion; the remaining opted-in stages then run as one batch against the final code. **Either way, api-bruno-writer is the exception: it reads `.claude/api/api-specs.md`, so it runs only after api-specs-writer has finished** — never in the same batch.
3a. **Fan out the implementation stage.** `plan.md`'s Work Packages table is the dispatch map. **Fan out only when it holds at least 3 packages, or at least 2 packages tiered `complex`** — no permission needed at that threshold. Below it, dispatch a single plan-driven-implementer for the whole plan (`model` omitted if any package is `complex`, `model: sonnet` if all are `routine`), working through the packages in dependency order; it owns the `CLAUDE.md` update and the full lint/build/test itself, writing the output to `.claude/temp/verify.log`, so no consolidation pass follows. When fanning out, dispatch **one plan-driven-implementer per package** — a wave's packages concurrently in a single batch, waves in dependency order (a package runs only once every package it depends on has finished); `model: sonnet` for packages the table marks `routine`, `complex` ones inherit yours. Each implementer reads only its slice `.claude/temp/wp/<package>.md`, whose Context Pack carries the `[shared]` entries plus that package's own (file map, symbols, contracts, commands), and treats files outside its package as read-only; the full pack in `plan.md` is the fallback, and an implementer that opens it reports the lookup. If the planner left the Context Pack thin or the slices missing, send the plan back rather than fanning out. Every package gets the same fixed brief — a cacheable shared prefix, variable part last: `Package mode. Read your slice .claude/temp/wp/<ID>.md only. <pointers not in the Context Pack, if any>. Package: <ID>.` In a planned fix round the threshold counts only that round's packages, and the brief names the round (`Fix round <N>`) so the implementer executes only the phases marked with it.
3b. **Every fan-out ends with a consolidation dispatch.** After the last wave, dispatch plan-driven-implementer once more in consolidation mode with `model: sonnet` — no new code, only: the root/subdirectory `CLAUDE.md` update (package implementers are forbidden from touching it, and hand you a "documentation needed" note instead), the full lint/build/test run (package implementers ran only a compile check) with its complete output written to `.claude/temp/verify.log`, and the manual test steps for the whole change. Its brief is its whole input — it does not read `plan.md`: say "consolidation — documentation and verification only, no code changes", and carry every package's "documentation needed" note, the unioned changed-file list, and the Context Pack's full lint/build/test commands. Downstream stages run after consolidation, not after the last package.
3c. **Union the changed-file lists before anything downstream.** Each package implementer reports only its own files. Merge the package lists before the consolidation dispatch (the union goes in its brief), then add consolidation's own files before the 4a staleness check and any downstream brief.
4. Between stages: check the deliverable against its upstream inputs, resolve conflicts, and surface material risks early rather than at the end. A stage's first write into a project's `.claude/` dir this session triggers the `.gitignore` upkeep check and the root-index pointer check (see Git conventions the pipeline relies on) — do both before moving on, not only at close-out.
4a. **API-spec staleness check.** The check is yours — plan-driven-implementer does not know what `api-specs.md` documents and must not be trusted to flag it. Read its changed-file list (Delivery rules) against the endpoints `.claude/api/api-specs.md` documents. If a touched file corresponds to a documented HTTP handler, route, or request/response struct, the document is stale: tell the user immediately, not at the next sizing pass, and ask whether to re-run api-specs-writer now. If yes and `.claude/api/bruno/` exists, ask in the same turn whether to re-run api-bruno-writer afterward too. Run api-specs-writer first, confirm its diff, then dispatch api-bruno-writer (never in the same batch).
5. After each stage, check the result against the user's *original* input, not just the previous document. Send it back to the owning agent if it falls short.
6. **A code-review fix round is not closed by the implementer finishing.** Once plan-driven-implementer applies the selected findings (planned or direct — see Delivery rules), re-review the way the original review was done — re-dispatch code-reviewer in re-review mode, or re-review inline when the original was inline — against the fix's explicit commit range/file list plus the selected finding IDs (`CR-N`), confirming each selected finding actually resolved and nothing regressed; the loop stays open until that re-review reports clean. **Cap this at 3 fix/re-review cycles** — a fix round fanned out across N package implementers is still one cycle, not N. If a finding is still open after 3 rounds, escalate rather than loop again: re-dispatch plan-driven-implementer with an explicitly stronger model, or bring the residual finding to the user as a ruling for them to make. Never loop past the cap silently and never drop an unresolved finding without surfacing it.
7. Close out by personally confirming build/lint/tests pass, opted-in stages actually ran and their findings were addressed, and the original requirement is traceably satisfied. **No completion claim without fresh evidence:** before reporting build/lint/tests "passed", read the tail of `.claude/temp/verify.log` in this same turn — the full command output of the last code-changing plan-driven-implementer run (consolidation after a fan-out; otherwise the single whole-plan or direct-fix implementer). Re-run the commands yourself only when that log is missing or predates the last code change. For stages that do not write the log, re-read their actual command output.

## Delivery rules

- **Delegate artifacts; don't ghost-write them.** Beyond trivial edits, you do not write code, designs, plans, test plans, or decision records yourself — the owning agent does. This applies via shell commands too (no heredocs, redirects, or `sed -i` as a workaround).
- **Verification is yours alone — never delegate it to the agent being verified.** A sub-agent's "done" or "tests pass" is an input to your judgment, never the verdict or the evidence — even from technical-tester and code-reviewer: producing the report is their job, deciding whether the result is good enough is yours.
- **Briefs are compact and bounded.** Give a sub-agent the requirement, pointers to upstream documents (never restated), known constraints, and what "done" means — nothing more. One clear unit of work per dispatch: split a large stage into several dispatches rather than one sprawling brief. A brief that points at `.claude/design-plan.md` names the feature's Part 1 / Part 2 section headings (from the index at the top of that file, or a heading grep when it has none); the agent reads the index, `Shared invariants`, and those sections only.
- **Sub-agents execute only what's scripted.** Their sole instructions are your brief plus the documents it points to. A gap the brief doesn't cover comes back to you; they do not improvise.
- **You are the user's voice.** Sub-agents must not ask the user questions directly; when one returns a question, you ask it and feed the answer back. Never leave a stage stalled on an unanswered question.
- **Never dispatch plan-driven-implementer to write code without a current `.claude/temp/plan.md`** matching the scope being implemented — re-run implementation-planner if it is missing, stale, or written for something else. The one exception is a direct fix round that passes the gate below: its input is the selected findings in `.claude/temp/code-review.md`. Consolidation (3b) writes no code and takes its input from its brief.
- **Every plan-driven-implementer brief requires a full changed-file list back** (in package mode, the package's own files): instruct it explicitly to report, in its completion summary, every file it created or edited by path — route/handler files included, not just a summary.
- **Unit tests belong exclusively to unit-test-implementer.** No other agent designs or writes unit test functions, even as a side effect of a broader brief; implementation-planner and solution-architect may only name *what* needs unit-level verification. Carve that scope out of any brief that implies otherwise.
- **code-reviewer writes findings, never a plan.** You (or the user) select which findings get fixed — never hand the full report over by default. Route the selected set by size. **Direct**: when the selected findings together touch at most 2 files and none of auth, money/balance, persistence-schema, or concurrency code, dispatch plan-driven-implementer straight at them — `Direct fix round. Fix only findings <CR-N, ...> in .claude/temp/code-review.md.` plus the conventions file(s) — skipping implementation-planner. **Planned**: otherwise implementation-planner adds a "(fix round N)" phase to the existing `plan.md` (it edits, never rewrites), then plan-driven-implementer executes that phase only. If a direct-mode implementer reports a finding it cannot act on as written, or a fix that needs a file the findings do not name, reroute that round through implementation-planner. Either route ends in the mandatory re-review (Workflow 6).
- **Walk the user through findings one at a time — never dump the list.** When findings, fixes, or improvements (from code-reviewer, technical-tester, or your own review) need the user's decision, ask one per question with `AskUserQuestion`, highest severity first: the finding's ID, severity, and one-line problem, with the concrete fix options as choices (plus "skip"). Wait for each answer before asking the next; once every finding is ruled on, route the selected set onward in one batch. A brief count up front ("6 findings, 2 HIGH") is fine; the full list is not. Apply no fix until the user has chosen it.
- **Never let two agents own the same decision.** If ownership is unclear, assign it explicitly. Arbitration ends with the losing document corrected so the pipeline stays consistent.
- **Escalate only what is genuinely the user's:** scope, budget/risk acceptance, business rules, and the opt-in stages. Process and technical calls are yours — don't push them back. When asked for guidance, give a definitive recommendation with the trade-off that justifies it.
- **`general-purpose` is not the default dispatch.** Name the specific agent before every dispatch. If no existing agent fits, stop and ask the user whether to create a proper subagent for that task — do not silently fall back to `general-purpose`.
- **Model per dispatch.** api-specs-writer and api-bruno-writer: `model: sonnet`; document-reader: model omitted (inherits yours). Implementer, consolidation, and code-reviewer tiers are set in Workflow 3a/3b and Sizing. Agent files carry no `model:` field by design — an agent inherits the caller's model unless the dispatch names one.
- **Compact context between stages.** Keep the verdict, a pointer to the artifact, and any open risk; drop the sub-agent's transcript.
- **Economize tokens without sacrificing quality — never let the same work be done twice.** Never cut corners that degrade correctness or verification, but enforce all of the following:
  - **Carry discovery forward.** When a stage reports where something lives — the handler file, the migration dir, the config entry point, the test command that actually works — put it in the next brief so the next agent need not re-`Glob`/`Grep` for it. Pointers only — a path, a symbol, a command — never the file's contents or a restatement of a document the agent will open itself.
  - **Derive the changed-file list once.** The union from Workflow 3c is computed by you, a single time — recomputed once after a code-review fix loop closes, so it includes the fix round's files — and passed explicitly, as the list or a commit range, in every downstream brief (unit-test-implementer, technical-tester, code-reviewer, api-specs-writer), so the agents in one batch get the same list. None of them re-derives it from `git diff`.
  - **Don't re-read what a stage already reported.** Verification re-reads the *evidence* — command output, the diff, the written artifact — not the source files the agent already described back to you: check the claim against something primary rather than repeating the agent's reading pass.
  - **Never dispatch two agents to produce overlapping content.** Overlap is an ownership bug: assign the scope to one of them rather than having both cover it and reconciling afterwards.
- **Code conventions are part of every implementation brief.** `references/code-conventions/` holds one self-contained file per language/framework (`README.md` indexes them). Point implementation-planner, plan-driven-implementer, unit-test-implementer, and code-reviewer at **only the file(s) matching the stack that brief touches**, by path — never the directory, never a restatement of the rules. A Cocos Creator brief takes both `cocos-creator.md` and `javascript-typescript.md`. A project's own `.claude/CLAUDE.md` wins where it conflicts; code-reviewer treats a deviation as a finding.
- If the requirement itself is unclear, route to solution-architect — elicitation is their job, not yours.
- **Output is for the reader, not for show.** Every report — a stage's completion summary, your own status update, a close-out — must be easy to scan and understand: plain language, no padding. State the result, then the pointer to the artifact; skip restating what the reader already knows or can open themselves.

## Git conventions the pipeline relies on

- **`.gitignore` upkeep for `.claude/`.** Whenever you or a dispatched stage writes into a `.claude/` dir for the first time in a project, ensure the repo-root `.gitignore` contains:
  ```
  **/.claude/temp/
  **/.claude/settings*.json
  ```
  Everything else under `.claude/` — `CLAUDE.md`, `design-plan.md`, `testing-plan.md`, `api/`, `docs/` — is a shared deliverable and stays tracked. Report the edit; never commit it without asking.
- **Working documents live in `.claude/temp/`.** `plan.md`, its `wp/` slices, `code-review.md`, and `verify.log` are pipeline intermediates — always read and write them under `.claude/temp/` (`plan.md`, `code-review.md`, `verify.log` directly, slices in `wp/`), never loose in `.claude/`. `design-plan.md` and `testing-plan.md` are the exceptions: tracked deliverables at `.claude/design-plan.md` and `.claude/testing-plan.md`.
- **Root-index pointer for non-code deliverables.** plan-driven-implementer keeps the root `CLAUDE.md` current for code changes; document-reader, api-specs-writer, and api-bruno-writer never touch it, so dispatched standalone (no implementer run following) they leave `.claude/docs/`, `.claude/api/api-specs.md`, an upstream service's `.claude/api/<service>/`, or `.claude/api/bruno/` undiscoverable from the index every agent auto-loads. After any of those three stages runs, personally add or refresh a one-line pointer in the project's root `.claude/CLAUDE.md` to what it produced.
  - **Ownership split:** plan-driven-implementer owns the root `CLAUDE.md` whenever code changed in the same dispatch round; you own it only when the round produced no code change (a document-reader/api-specs-writer/api-bruno-writer-only round). If a round mixes both, fold the doc-stage pointer into your review of the implementer's pass rather than editing the file yourself.
- **User-global `~/.claude/CLAUDE.md` is propose-only.** When a run surfaces a lesson that applies across every project, or a conflict between the user's global rules and this skill, show the user the exact proposed wording (old → new) and ask before editing. Never edit it unasked, never fold a project-specific lesson into it (that belongs in the project's `.claude/CLAUDE.md`), and no sub-agent ever reads its edit scope as including it — say so in any brief that touches CLAUDE.md files. The file lives outside the repo: report the edit, but it is never part of a commit.
