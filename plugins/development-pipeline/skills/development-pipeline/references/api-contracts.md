# API contracts and source documents

Read when `SKILL.md` Sizing sends you here. Part of the orchestrator rules in `SKILL.md`; "the sizing call" is its one opt-in `AskUserQuestion`.

- **API contracts are a required input for integration work.** When a workstream calls or implements an HTTP API, point every design, implementation, test, and review brief at the contract: `.claude/api/api-specs.md` for this project's own API, `.claude/api/<service>/api-specs.md` for one it consumes from another service. Vendor a missing upstream spec first (rule below) — never let an agent infer a third party's contract from the calling code.
- **Frontend-consumes-backend is the common case of that rule — no separate agent.** A plan or implementer brief with the frontend calling this project's own backend points at `.claude/api/api-specs.md`, never at the backend source. For an endpoint this delivery adds or changes, `.claude/design-plan.md` Part 2 (or the plan's Context Pack `Contracts` excerpt of it) is the contract until api-specs-writer documents it. Otherwise, if that file is missing or lacks the endpoints in scope, the consuming stage stops and reports `contract missing: <path>` — never falls back to the backend source; you then ask the user once whether to run api-specs-writer or abort. Never dispatch it unasked.
- **Vendoring an upstream spec is never api-specs-writer's job — it documents this project's own code only.** Every upstream service gets its own subdirectory directly under `.claude/api/`, whatever the source type — never a flat `<service>-api-specs.md` file. Route by source:
  - **Machine-readable spec exists** (OpenAPI/Swagger YAML or JSON, a Postman collection export, another repo's own `api-specs.md`): copy it yourself, verbatim, into `.claude/api/<service>/` — as `api-specs.md` when the source is already in that shape, otherwise under its original filename (`openapi.yaml`, `collection.json`) — with a provenance header (source path/URL, date copied). No agent, no rewriting.
  - **Prose-only source** (PDF, Word doc, wiki/integration guide): when document-reader is selected in the sizing call, dispatch it once, telling it the document is an upstream API contract and giving it the `<service>` slug; it writes `.claude/docs/<vendor>/...md` and, in the same pass, `.claude/api/<service>/api-specs.md` in the house shape. No second stage.
  - Point every consuming brief at whichever of `.claude/api/<service>/api-specs.md` or `.claude/docs/<vendor>/...md` actually holds the contract — don't leave it to be found.
- **This whole pipeline (api-specs-writer, api-bruno-writer, upstream vendoring) is HTTP-only.** gRPC (or any other IDL-defined protocol) is out of scope by design: the checked-in `.proto` already *is* the canonical, machine-readable contract. Point every brief touching a gRPC service — this project's or an upstream's — straight at its `.proto` file(s): no api-specs-writer pass, no document-reader summary, no house `-specs.md` file. Fall back to document-reader only if the `.proto` is genuinely unavailable and the only description is prose.
- **Source documents go through a summary check first.** Before any stage reads an API spec, PDF, Word doc, or Postman collection, check `.claude/docs/` for a summary; if one exists, point the consuming agent at it — never re-read or re-summarize a distilled document. If none exists, fold the choice into the same sizing call rather than asking separately: document-reader is an option of its documentation-stages question, and leaving it unselected means the consuming stage reads the original this once.
- **Staleness check (`SKILL.md` Workflow 4a).** The check is yours — plan-driven-implementer does not know what `api-specs.md` documents and must not be trusted to flag it. The document holds the API contract only, never code structure, so it goes stale only when what a caller sees changes. Grep the diff of the changed files that hold a route, handler, middleware, or request/response type for a change to a documented endpoint's path, method, header, request or response field, status or error code, or caller-visible behaviour (idempotency, a side effect). A pure refactor — a moved file, a renamed struct or function, a split package — does not make it stale. If the contract changed, the document is stale: tell the user immediately, not at the next sizing pass, and ask whether to re-run api-specs-writer now. If yes and a collection exists under `.claude/api/bruno/<collection-slug>/`, ask in the same turn whether to re-run api-bruno-writer afterward too. Run api-specs-writer first, confirm its diff, then dispatch api-bruno-writer.
