# Fix rounds

Read before acting on a code-review finding the user selected or on a failing `verify.log`. Part of the orchestrator rules in `SKILL.md`. The sensitive areas named below are auth, money/balance, persistence-schema, and concurrency code.

## Routing selected review findings

**code-reviewer writes findings, never a plan.** You (or the user) select which findings get fixed — never hand the full report over by default. Route the selected set by size. **Direct**: when the selected findings together touch at most 2 files and none of auth, money/balance, persistence-schema, or concurrency code, dispatch plan-driven-implementer straight at them — `Direct fix round. Fix only findings <CR-N, ...> in .claude/temp/code-review.md.` plus the conventions file(s) and the full lint/build/test commands (copied from `plan.md`'s Context Pack when a plan exists, from the project's `CLAUDE.md` otherwise) — skipping implementation-planner. **Planned**: otherwise implementation-planner adds a "(fix round N)" phase to the existing `plan.md` (it edits, never rewrites), then plan-driven-implementer executes that phase only. If a direct-mode implementer reports a finding it cannot act on as written, or a fix that needs a file the findings do not name, reroute that round through implementation-planner. Either route ends in the mandatory re-review (the loop below).

## Verification fix round

**A failing `verify.log` gets a verification fix round, never a silent retry.** When the log — from consolidation or a single implementer — shows a non-zero lint/build/test exit, fix it before any downstream stage runs, and first classify each failure by where the fix lies. **Product code at fault**: map the failing files to their owning package through `plan.md`'s Work Packages table, then apply the same gate as above (Routing) — *direct* (at most 2 files, none of those sensitive areas): dispatch plan-driven-implementer with `Direct fix round — verification fix.` plus the failing `verify.log` lines, the files they name, the conventions file(s), and the full lint/build/test commands (sourced as above); *planned*: otherwise implementation-planner adds a "(fix round N)" phase for the failures, assigned to the owning package(s), then plan-driven-implementer executes that phase only. **A test stale against the intended behaviour**: never plan-driven-implementer, which may not touch a test file — dispatch unit-test-implementer with `Verification fix — stale test.` plus the failing `verify.log` lines, the test files they name, and the intended change, for that purpose only. When unit tests were not opted in, ask the user first with `AskUserQuestion` — fix the stale tests with unit-test-implementer, or leave them failing and stop — and dispatch only on a yes; never dispatch it unasked. When unit tests are opted in, keep that agent: run the later unit-test stage by continuing it (`SendMessage`) so it does not re-read what it just edited, and dispatch fresh only if it is no longer available. **Unclear which is at fault**: bring it to the user as a ruling. Either way verification re-runs afterwards and you check it as in `SKILL.md` Workflow 7 — the fixing implementer rewrites `verify.log`, consolidation does after a fanned-out round, and after a unit-test-implementer fix the log predates the change, so `SKILL.md` Workflow 7's re-run applies. These rounds count against the loop's cap of 3 cycles and escalate the same way.

## The fix/re-review loop

**A code-review fix round is not closed by the implementer finishing.** Before each code-review fix round — and only then — save the current diff to `.claude/temp/pre-fix.diff` yourself — `git diff HEAD`, plus `git diff --no-index /dev/null <file>` for each untracked file, redirected into it; this snapshot is one of the two redirects `SKILL.md` Delivery rules permit you. Keep it until that cycle's re-review: a verification fix round inside the cycle does not overwrite it; the next code-review fix round replaces it. Once plan-driven-implementer applies the selected findings (planned or direct — see Routing above), re-review the way the original review was done — re-dispatch code-reviewer in re-review mode, or re-review inline when the original was inline — with a brief naming the cycle's changed-file list (the files of any verification fix inside it included), that snapshot, and the selected finding IDs (`CR-N`): the re-review compares the current code against the snapshot, confirming each selected finding actually resolved and nothing regressed. Walk the user through every new finding the re-review raises (`SKILL.md` Delivery rules): the ones the user selects start the next cycle; the ones the user skips count as "not selected" — closed now, and carried over under that tag by any later re-review. The loop ends when no selected finding is open — every selected finding Resolved and every new finding ruled on; "not selected" findings never hold it open. **Cap this at 3 fix/re-review cycles** — a fix round fanned out across N package implementers is still one cycle, not N, and a verification fix round (above) counts against the same cap. If a finding is still open after 3 rounds, escalate rather than loop again: re-dispatch plan-driven-implementer with an explicitly stronger model, or bring the residual finding to the user as a ruling for them to make. Never loop past the cap silently and never drop an unresolved finding without surfacing it. **Once a fix round closes, every downstream brief (unit-test-implementer, technical-tester, api-specs-writer) names the fixed finding IDs (`CR-N`) and points at `.claude/temp/code-review.md` as an input that overrides `plan.md` where the two differ** — a pointer only, never the findings restated: a fix can change behaviour beyond what `plan.md` records, and a stage reading the plan alone derives a stale expectation.
