# Fix rounds

Read before acting on a code-review finding the user selected, a failing `verify.log`, or a failing technical-test case in `test-results.md`. Part of the orchestrator rules in `SKILL.md`. **You number fix rounds:** `N` is one counter per plan, rising across every kind of round — review, verification, technical-test — and every brief for the round (planner, implementer, technical-tester) states `Fix round <N>` (the planner's also whether unit tests are opted in); the planner never picks the number. Throughout, "the implementer" means plan-driven-implementer — with the `CDK rules:` path when the round touches CDK files (`SKILL.md` 3b).

## Routing selected review findings

Route the selected findings by size. **Direct**: when the selected findings together touch at most 2 files, one owner (`app` or `cdk`), and no sensitive area, dispatch the implementer straight at them — `Direct fix round. Fix only findings <CR-N, ...> in .claude/temp/code-review.md.` plus the conventions file(s) and the full lint/build/test commands (from the planner's handback, or a grep of `plan.md`'s `[shared] Commands` entries when it is no longer in context; from the project's `CLAUDE.md` when no plan exists) — skipping implementation-planner. **Planned**: otherwise implementation-planner adds a "(fix round N)" phase to the existing `plan.md` (it edits, never rewrites), then the implementer executes that phase only. If a direct-mode implementer reports a finding it cannot act on as written, or a fix that needs a file the findings do not name, reroute that round through implementation-planner. A finding you raise yourself, absent from `code-review.md`, is routed the same way once the user selects it: give it the next `CR-N` (source: orchestrator) in the implementer and re-review briefs, and the re-review records it in `.claude/temp/code-review.md` — never fix it unrecorded. Either route ends in the mandatory re-review (the loop below).

## Verification fix round

**A failing `verify.log` gets a verification fix round, never a silent retry.** When the log — from consolidation or a single implementer — shows a non-zero lint/build/test exit, fix it before any downstream stage runs, and first classify each failure by where the fix lies. **Product code at fault**: map the failing files to their owning package through `plan.md`'s Work Packages table (a failing file no package owns goes the planned route: implementation-planner assigns it to a package, or a new one, in the fix-round phase), then apply the same gate as above (Routing) — *direct* (at most 2 files, one owner, no sensitive area): dispatch the implementer with `Direct fix round — verification fix.` plus the failing `verify.log` lines and the files they name, the rest of the brief as in Routing; *planned*: otherwise implementation-planner adds a "(fix round N)" phase for the failures, assigned to the owning package(s), then the implementer executes that phase only. **A test stale against the intended behaviour** (the stale-test question): dispatch the implementer with `Verification fix — stale test.` plus the failing `verify.log` lines (or the failing `test-results.md` command lines), the test files they name, the intended change, and the `Unit tests:` path, for that purpose only. When unit tests were not opted in, ask the user first with `AskUserQuestion` — update the stale tests, or leave them failing and stop — and dispatch only on a yes; never dispatch it unasked. On "leave failing", skip the remaining downstream stages and close out reporting the delivery as incomplete — name each failing test and its `verify.log` line, and make no build/tests-passed claim. **Unclear which is at fault**: bring it to the user as a ruling. Verification then re-runs and you check it per `SKILL.md` Workflow 7: the fixing implementer (or consolidation, after a fan-out) rewrites `verify.log`; a failure there opens the next fix round (next `N`, same cap), classified as above.

## Unit-test and technical-test failures

**A failing case in `test-results.md` is routed like a failing `verify.log`.** Classify it the same way — product code at fault goes through the Verification fix round gate above (with the failing lines, case IDs and reproduction steps, or for a divergence the plan/design line and the code's actual behaviour); an expectation the stage got wrong goes back to the agent that wrote it (the implementer for a unit test, or technical-tester) with the derivation; a contradiction between sources is a ruling for the user. A spec/code divergence any stage reports — technical-tester or an implementer (code or a test written to one behaviour where the plan or design says another) — is classified the same way, as if it had failed: product code at fault opens a fix round, after which the stage that wrote the test re-checks that expectation. **When technical-tester's handback reports `expectation corrected` cases, check each derivation against its named source (the plan, the design, a named finding, or the code) before accepting the run**; a correction you reject is a failing case, routed as above. An expectation fix is a fix round like any other: it takes the next `N` and counts toward the cap. After the fix, the implementer's `verify.log` re-runs the unit tests, and technical-tester re-runs (re-run mode, brief listing the case IDs, changed files, and whether `.claude/temp/verify.log` is current) the failed cases plus any case touching the changed files. **When code review is in scope and any fix round after the review loop closed (verification or technical-test) touches a sensitive area or a file the review covered**, snapshot and re-review that round's files as in the code-review loop below before close-out — a brief with the snapshot and no finding IDs (code-reviewer's snapshot-only re-review); its new findings are walked and routed as in the loop below, under the same cap.

**New behaviour from any fix round gets unit coverage when unit tests are opted in.** implementation-planner names a unit target for each behaviour a planned fix round adds or changes; for a direct round, name the changed behaviour in the implementer brief yourself. The fixing implementer writes those tests in the same pass (its brief carries the `Unit tests:` path).

## The fix/re-review loop

**A code-review fix round is not closed by the implementer finishing.** Before each code-review fix round, and before any later fix round that Unit-test and technical-test failures (above) sends to re-review, save the current diff to `.claude/temp/pre-fix.diff` yourself — `git diff HEAD` redirected into it — and copy each untracked changed file to `.claude/temp/pre-fix/<path>` (`mkdir -p` + `cp`; a new repo with no commit is all untracked) and name that dir in the re-review brief too. Keep it until that cycle's re-review: a verification fix round inside the cycle does not overwrite it; the next code-review fix round replaces it. Once the implementer applies the selected findings (planned or direct — see Routing above), re-review per `references/code-review.md` — with a brief naming the cycle's changed-file list (the files of any verification fix inside it included), that snapshot, and the selected finding IDs (`CR-N`): the re-review compares the current code against the snapshot, confirming each selected finding actually resolved and nothing regressed. Walk the user through every new finding the re-review raises (`SKILL.md` Delivery rules): the ones the user selects start the next cycle; the ones the user skips count as "not selected" — closed now, and carried over under that tag by any later re-review. The loop ends when no selected finding is open — every selected finding Resolved and every new finding ruled on; "not selected" findings never hold it open. **Cap this at 3 fix/re-review cycles**, counted per selected finding or failure — the rounds it has been in, never the round number `N` — a fix round fanned out across several package implementers is still one cycle. If a finding is still open after 3 rounds, escalate rather than loop again, per the `SKILL.md` model table (escalation row). The escalated attempt is the last one: it is not a fourth ordinary cycle, and if its re-review still leaves the finding open, stop and bring the user a ruling — never a further round. A ruling names each unresolved finding by ID with its evidence and asks whether to accept the risk, narrow the scope, or abandon; until the user rules, the close-out reports the delivery as incomplete, never as passing. **Once a fix round closes, every downstream brief (technical-tester, api-specs-writer) names the fixed finding IDs (`CR-N`) and points at `.claude/temp/code-review.md` as an input that overrides `plan.md` where the two differ** — a pointer only, never the findings restated: a fix can change behaviour beyond what `plan.md` records, and a stage reading the plan alone derives a stale expectation.
