# Fix rounds

Read before acting on a code-review finding the user selected, a failing `verify.log`, or a failing technical-test case in `test-results.md`. Part of the orchestrator rules in `SKILL.md`. "Sensitive areas" are defined in `SKILL.md`. **You number fix rounds:** `N` is one counter per plan, rising across every kind of round — review, verification, technical-test — and every planner and implementer brief for the round states `Fix round <N>`; the planner never picks the number. A fix round whose files span both `app` and `cdk` owners is never direct. Throughout, "the implementer" means plan-driven-implementer, or cdk-implementer for `cdk`-owned files; a mixed plan's planned fix rounds fan out (`SKILL.md` 3b).

## Routing selected review findings

Route the selected findings by size. **Direct**: when the selected findings together touch at most 2 files and no sensitive area, dispatch the implementer straight at them — `Direct fix round. Fix only findings <CR-N, ...> in .claude/temp/code-review.md.` plus the conventions file(s) and the full lint/build/test commands (copied from `plan.md`'s Context Pack when a plan exists, from the project's `CLAUDE.md` otherwise) — skipping implementation-planner. **Planned**: otherwise implementation-planner adds a "(fix round N)" phase to the existing `plan.md` (it edits, never rewrites), then the implementer executes that phase only. If a direct-mode implementer reports a finding it cannot act on as written, or a fix that needs a file the findings do not name, reroute that round through implementation-planner. Either route ends in the mandatory re-review (the loop below).

## Verification fix round

**A failing `verify.log` gets a verification fix round, never a silent retry.** When the log — from consolidation or a single implementer — shows a non-zero lint/build/test exit, fix it before any downstream stage runs, and first classify each failure by where the fix lies. **Product code at fault**: map the failing files to their owning package through `plan.md`'s Work Packages table, then apply the same gate as above (Routing) — *direct* (at most 2 files, no sensitive area): dispatch the implementer with `Direct fix round — verification fix.` plus the failing `verify.log` lines and the files they name, the rest of the brief as in Routing above; *planned*: otherwise implementation-planner adds a "(fix round N)" phase for the failures, assigned to the owning package(s), then the implementer executes that phase only. **A test stale against the intended behaviour**: never plan-driven-implementer, which may not touch a test file — dispatch unit-test-implementer with `Verification fix — stale test.` plus the failing `verify.log` lines, the test files they name, and the intended change, for that purpose only. When unit tests were not opted in, ask the user first with `AskUserQuestion` — fix the stale tests with unit-test-implementer, or leave them failing and stop — and dispatch only on a yes; never dispatch it unasked. When unit tests are opted in, keep that agent: run the later unit-test stage by continuing it (`SendMessage`) so it does not re-read what it just edited, and dispatch fresh only if it is no longer available. **Unclear which is at fault**: bring it to the user as a ruling. Either way verification re-runs afterwards and you check it as in `SKILL.md` Workflow 7 — the fixing implementer rewrites `verify.log`, consolidation does after a fanned-out round, and after a unit-test-implementer fix the log predates the change, so `SKILL.md` Workflow 7's re-run applies. These rounds count against the loop's cap of 3 cycles and escalate the same way.

## Technical-test failures

**A failing case in `test-results.md` is routed like a failing `verify.log`.** Classify it the same way — product code at fault goes through the Verification fix round gate above (failing case IDs and their reproduction steps in place of log lines); an expectation the tester got wrong goes back to technical-tester with the derivation; a contradiction between sources is a ruling for the user. After the fix, technical-tester re-runs (re-run mode, brief listing the case IDs and changed files) the failed cases plus any case touching the changed files — the latest marker per case ID is the evidence — and the round counts against the same cap of 3. **When code review is in scope and any fix round after the review loop closed (verification or technical-test) touches a sensitive area or a file the review covered**, snapshot and re-review that round's files as in the code-review loop below before close-out.

**New behaviour from any fix round gets unit coverage when unit tests are opted in.** implementation-planner names a unit target for each behaviour a planned fix round adds or changes; for a direct round, name the changed behaviour in the unit-test-implementer brief yourself. Continue unit-test-implementer for those targets before close-out, even when the unit-test stage already ran — or dispatch it fresh when that stage has not run yet.

## The fix/re-review loop

**A code-review fix round is not closed by the implementer finishing.** Before each code-review fix round — and only then — save the current diff to `.claude/temp/pre-fix.diff` yourself — `git diff HEAD` redirected into it — and, since a diff against `/dev/null` is no baseline, copy each untracked changed file to `.claude/temp/pre-fix/<path>` (`mkdir -p` + `cp`; a new repo with no commit is all untracked) and name that dir in the re-review brief too; this snapshot is one of the redirects `SKILL.md` Delivery rules permit you. Keep it until that cycle's re-review: a verification fix round inside the cycle does not overwrite it; the next code-review fix round replaces it. Once the implementer applies the selected findings (planned or direct — see Routing above), re-review the way the original review was done — re-dispatch code-reviewer in re-review mode, or re-review inline when the original was inline and the fix round's files still pass the inline gate (`references/code-review.md`) — with a brief naming the cycle's changed-file list (the files of any verification fix inside it included), that snapshot, and the selected finding IDs (`CR-N`): the re-review compares the current code against the snapshot, confirming each selected finding actually resolved and nothing regressed. Walk the user through every new finding the re-review raises (`SKILL.md` Delivery rules): the ones the user selects start the next cycle; the ones the user skips count as "not selected" — closed now, and carried over under that tag by any later re-review. The loop ends when no selected finding is open — every selected finding Resolved and every new finding ruled on; "not selected" findings never hold it open. **Cap this at 3 fix/re-review cycles**, counted per selected finding or failure — the rounds it has been in, never the round number `N` — a fix round fanned out across N package implementers is still one cycle, not N, and a verification fix round (above) counts against the same cap. If a finding is still open after 3 rounds, escalate rather than loop again: re-dispatch the implementer with an explicitly stronger model, or bring the residual finding to the user as a ruling for them to make. Never loop past the cap silently and never drop an unresolved finding without surfacing it. **Once a fix round closes, every downstream brief (unit-test-implementer, technical-tester) names the fixed finding IDs (`CR-N`) and points at `.claude/temp/code-review.md` as an input that overrides `plan.md` where the two differ** — a pointer only, never the findings restated: a fix can change behaviour beyond what `plan.md` records, and a stage reading the plan alone derives a stale expectation.
