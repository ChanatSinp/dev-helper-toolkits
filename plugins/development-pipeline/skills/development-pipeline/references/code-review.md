# Code review

Read before running an opted-in code review or re-review. Part of the orchestrator rules in `SKILL.md`.

- **Review first.** Alongside other post-implementation stages, code review (dispatched or inline) and its fix/re-review loop (`references/fix-rounds.md`) run first, to completion; the remaining opted-in stages then run as one batch against the final code, api-bruno-writer still after api-specs-writer.
- **Review inline yourself** when the change touches at most 2 files, adds no new module or directory, and touches no sensitive area: read `../../agents/code-reviewer.md` first, then read the diff, apply its methodology and severity scale, and write the same `.claude/temp/code-review.md`. Otherwise **dispatch code-reviewer**, model per the `SKILL.md` table.
- **Its brief carries only** the changed-file list, the `plan.md` Context Pack path (when a plan exists; otherwise a pointer to the project's `.claude/CLAUDE.md`), the conventions file(s), and, when they apply, the API contract path (per `references/api-contracts.md`) and the design-pattern file (`SKILL.md`); it reads the changed files and their direct callees/callers, never the wider repo. A re-review runs the same way as the review it re-checks (inline or dispatched) — unless the fix round's files fail the inline gate above, then dispatch code-reviewer — and its brief adds the cycle's changed-file list, the pre-fix snapshot, and the selected finding IDs — none for a snapshot-only re-review (`references/fix-rounds.md`).
- **Check the report is from this run.** After any dispatched review, confirm `.claude/temp/code-review.md` is current — its heading time and Summary name this change — before reading or routing a finding from it; send it back to code-reviewer if it is stale.
